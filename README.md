# Transactions API

REST API built with Java and Spring Boot for storing, replacing, querying and importing linked transactions.

This version persists transactions in MySQL and protects the transaction graph against cyclic relationships, partial batch writes and concurrent graph mutations.

## Features

- Create or replace transactions through `PUT`.
- Persist transactions in MySQL.
- Retrieve transaction IDs by type.
- Calculate the total amount of a transaction and all of its transitive descendants.
- Import transactions from CSV.
- Allow out-of-order parent references.
- Reject self-referencing and indirect cyclic relationships before persistence.
- Execute CSV imports atomically.
- Serialize graph mutations through a database-backed pessimistic lock.
- Manage database schema changes with Flyway.
- Run integration tests against real MySQL instances with Testcontainers.
- Start and verify the complete application through Docker Compose.
- Automate common development workflows through a Claude Code project skill.

# Architecture

The application follows a layered architecture with persistence and concurrency concerns separated from the business logic.

```text
HTTP Request
     |
     v
TransactionController
     |
     +----------------------+
     |                      |
     v                      v
TransactionService     TransactionCsvParser
     |
     +----------------------+
     |                      |
     v                      v
Cycle Validation    TransactionGraphLockManager
                            |
                            v
                   Pessimistic DB Lock
     |
     v
TransactionRepository
     |
     v
JpaTransactionRepositoryAdapter
     |
     v
SpringDataTransactionRepository
     |
     v
Hibernate / JPA
     |
     v
MySQL
```

Responsibilities are separated as follows:

- **Controller**: handles HTTP requests and responses.
- **DTOs**: define the HTTP API contract.
- **CSV parser**: parses and validates uploaded CSV files.
- **Service**: contains transaction and graph business rules.
- **Cycle validation**: validates the future graph before any graph mutation is persisted.
- **Graph lock manager**: serializes graph mutations using a database-backed pessimistic lock.
- **Repository abstraction**: keeps the service independent from Spring Data JPA.
- **JPA adapter**: maps the repository abstraction to Spring Data JPA.
- **Flyway**: owns database schema evolution.
- **Global exception handler**: converts expected application errors into consistent HTTP responses.

# Transaction Model

A transaction contains:

```text
id
amount
type
parentId
```

`parentId` is optional.

It represents the parent transaction in the transaction graph.

For example:

```text
10
└── 11
    └── 12
```

means:

```text
11.parent_id = 10
12.parent_id = 11
```

Transaction IDs are supplied by the client and are not generated by the application.

Saving an already existing transaction ID replaces its current state.

# API

## Create or replace a transaction

```http
PUT /transactions/{transactionId}
```

Example:

```json
{
  "amount": 5000,
  "type": "cars"
}
```

Transaction with parent:

```json
{
  "amount": 10000,
  "type": "shopping",
  "parent_id": 10
}
```

Successful response:

```json
{
  "status": "ok"
}
```

Sending another `PUT` request with the same transaction ID replaces the existing transaction.

Replacement includes:

```text
amount
type
parent_id
```

The replacement is validated against the complete resulting graph before it is stored.

---

## Find transactions by type

```http
GET /transactions/types/{type}
```

Example:

```http
GET /transactions/types/shopping
```

Response:

```json
[
  11,
  12
]
```

IDs are returned in ascending order.

If no transactions exist for the requested type:

```json
[]
```

with HTTP `200 OK`.

---

## Calculate transaction sum

```http
GET /transactions/sum/{transactionId}
```

The result includes the requested transaction plus all transitively connected descendants.

Example:

```text
10 → 5000
└── 11 → 10000
    └── 12 → 5000
```

Request:

```http
GET /transactions/sum/10
```

Response:

```json
{
  "sum": 20000.0
}
```

Request:

```http
GET /transactions/sum/11
```

Response:

```json
{
  "sum": 15000.0
}
```

If the requested transaction does not exist:

```http
HTTP 404 Not Found
```

Example response:

```json
{
  "status": 404,
  "error": "Not Found",
  "message": "Transaction not found with id: 999"
}
```

# CSV Import

Multiple transactions can be imported through:

```http
POST /transactions/import
Content-Type: multipart/form-data
```

The multipart field must be named:

```text
file
```

Required CSV headers:

```csv
id,amount,type,parent_id
```

Example:

```csv
id,amount,type,parent_id
100,5000,cars,
101,10000,shopping,100
102,5000,shopping,101
```

`parent_id` may be empty.

Successful response:

```json
{
  "imported": 3
}
```

The complete file is parsed before persistence.

The complete candidate graph is also validated before persistence.

The import therefore behaves atomically:

```text
valid complete batch
        |
        v
      commit
```

while:

```text
invalid row
cycle
database error
        |
        v
     rollback
```

A failed batch does not persist a valid prefix.

Existing transaction IDs may also be replaced through CSV using the same replacement semantics as the `PUT` endpoint.

Duplicate IDs inside the same CSV file are rejected.

# Cycle Prevention

Relationships between transactions form a directed graph.

For example:

```text
A → B
B → A
```

would form a cycle and is rejected.

Cycle prevention happens before persistence.

For a write operation, the service:

```text
acquires graph write lock
        |
        v
loads the current graph
        |
        v
applies proposed changes in memory
        |
        v
validates the resulting graph
        |
        +---- cycle ----> reject
        |
        v
persist
        |
        v
commit
```

A cyclic mutation returns:

```http
HTTP 409 Conflict
```

The validation applies to:

- Individual `PUT` operations.
- Replacements of existing transactions.
- CSV batches.
- Relationships involving records already stored in MySQL.

The sum traversal also retains a defensive `visited` set.

Therefore the application contains two protections:

```text
WRITE → prevent invalid cycles from being stored

READ  → defensively avoid revisiting nodes
```

---

# Out-of-Order Parent Relationships

A transaction may reference a parent that does not exist yet.

For example, this is valid:

```text
transaction 20
parent_id = 10
```

even when transaction `10` has not yet been stored.

Transaction `10` may be created later.

Because this behavior is intentional, `parent_id` does not use a database foreign key.

The database still indexes `parent_id` for query efficiency.

# Transactions and Atomicity

Individual writes and CSV writes execute inside Spring database transactions.

Conceptually:

```text
@Transactional
        |
        v
acquire graph lock
        |
        v
validate resulting graph
        |
        v
persist
        |
        v
commit
```

Batch operations use `saveAllAndFlush()` while the service transaction is still active.

This deliberately forces persistence errors to surface inside the transaction boundary.

If any row fails:

```text
entire batch
    |
    v
rollback
```

Existing committed state remains unchanged.

# Concurrent Graph Mutations

Cycle validation by itself is not sufficient under concurrent writes.

Consider two requests executing simultaneously:

```text
Request 1              Request 2

A → B                  B → A

validate OK            validate OK
save                    save
```

Without coordination, each request could validate against the old graph and the combined result could become cyclic.

To prevent this, graph mutations use a database-backed pessimistic lock.

The lock repository uses:

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
```

Conceptually this behaves like:

```sql
SELECT ...
FOR UPDATE;
```

All graph mutations acquire the same reserved lock before reading the graph.

Therefore writes are serialized:

```text
writer 1
   |
   v
graph lock
   |
   +------ writer 2 waits
   |
validate
persist
commit
   |
release
   |
   v
writer 2 continues
```

---

## Concurrency Trade-Off

The global graph lock intentionally prioritizes correctness over maximum write throughput.

Advantages:

```text
simple concurrency model
strong graph consistency
easy to reason about
easy to test
```

Trade-off:

```text
graph writes are serialized
```

For the scope of this challenge, preserving graph integrity is considered more important than maximizing write throughput.

A production system with substantially higher write requirements could move toward finer-grained locking or a different graph consistency strategy.

# Sum Algorithm

For each sum operation, the application reads the current transactions and builds temporary lookup structures:

```text
transactionId → transaction

parentId → children
```

An iterative Depth First Search traverses all descendants.

A `Set<Long>` tracks visited transaction IDs.

This:

- prevents counting a transaction twice;
- provides defensive protection if inconsistent cyclic data somehow exists;
- avoids recursion depth limitations.

Approximate complexity:

```text
Time:  O(n)
Space: O(n)
```

for `n` persisted transactions.

The implementation favors correctness and simplicity over premature optimization.

---

# Money Representation

The challenge contract uses `double` for transaction amounts, so this implementation preserves that type.

For a production financial application, `BigDecimal` or integer minor units would generally be preferred to avoid floating-point precision issues.

# Error Handling

Expected application failures use a consistent structure:

```json

  "status": 400,
  "error": "Bad Request",
  "message": "Description of the error"
}
```

Handled cases include:

```text
400 Bad Request
- invalid request validation
- malformed JSON
- invalid path parameter types
- missing multipart file
- empty CSV file
- malformed CSV
- invalid CSV numeric values

404 Not Found
- requested transaction does not exist

409 Conflict
- mutation would produce a cyclic graph
```

Unexpected infrastructure or programming errors are not silently converted into client errors and remain server errors.

# Design Decisions

## Repository abstraction

`TransactionService` depends on:

```text
TransactionRepository
```

instead of depending directly on Spring Data JPA.

This keeps the application business logic independent from the persistence technology.

---

## Flyway owns schema changes

Schema evolution is explicit and versioned.

Hibernate does not mutate the schema automatically.

This avoids having application startup silently change production database structures.

---

## No foreign key on `parent_id`

Parent records may arrive out of order.

A database foreign key would prevent this valid use case.

Cycle integrity is therefore enforced at the application graph level instead.

---

## Global graph write lock

The lock is deliberately global.

This is simpler and safer for the scope of the challenge than attempting fine-grained graph locking.

The trade-off is reduced concurrent write throughput.

---

## Defensive read traversal

Cycles are prevented during writes.

The read algorithm still maintains a `visited` set as a secondary defensive mechanism.

This protects traversal even if inconsistent historical data were introduced externally.

---

## Iterative traversal

The graph traversal uses an explicit `Deque`.

It does not rely on recursive method calls.

This avoids stack-depth problems for unusually deep graphs.

---

## CSV atomicity

CSV parsing and graph validation occur before persistence.

Persistence itself runs in a database transaction.

Therefore both application validation failures and database persistence failures avoid partial imports.

---

# Assumptions

- Transaction IDs are supplied by clients.
- `parent_id` is optional.
- Parent transactions may arrive after their children.
- Existing transaction IDs are replaced rather than duplicated.
- Type lookup responses return IDs in ascending order.
- CSV files require `id`, `amount`, `type`, and `parent_id`.
- A CSV batch cannot contain the same transaction ID more than once.
- Transaction amounts remain `double` because that is the challenge contract.
- Graph correctness is prioritized over maximum concurrent write throughput.
